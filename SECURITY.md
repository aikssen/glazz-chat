# Security Policy

Glazz handles authentication, session material, provider credentials, and user
conversation data. Security reports are welcome and are treated as a priority over
feature work.

## Supported versions

Glazz is pre-1.0 and under active development. Only the latest tagged release and
the current `main` branch receive fixes.

| Version               | Supported |
| --------------------- | --------- |
| `main`                | Yes       |
| Latest `v0.x.0` tag   | Yes       |
| Earlier `v0.x.0` tags | No        |

Glazz is not yet approved for public production traffic. See
[Security and Production Readiness](./docs/security-production-readiness.md) for the
control matrix, open risks, and launch gates.

## Reporting a vulnerability

Report privately through GitHub, never in a public issue, pull request, or
discussion:

1. Open the [Security tab](https://github.com/aikssen/glazz-chat/security) of this
   repository.
2. Choose **Report a vulnerability** to open a private security advisory.

Private vulnerability reporting keeps the report visible only to you and the
maintainer until a fix is published.

## What to include

A report is easier to reproduce and fix when it contains:

- affected component (`apps/api`, `apps/web`, worker, contracts, deployment);
- affected version, tag, or commit;
- preconditions such as guest, registered user, or administrator role;
- reproduction steps or a proof of concept;
- observed impact and the impact you believe is achievable;
- any logs or requests with credentials and personal data removed.

## Response targets

These are targets for a single-maintainer project, not a contractual SLA:

| Stage                        | Target                                           |
| ---------------------------- | ------------------------------------------------ |
| Acknowledgement              | 5 business days                                  |
| Initial assessment           | 10 business days                                 |
| Fix or documented mitigation | Severity-dependent, communicated in the advisory |

## Disclosure

Please allow a fix to ship before publishing details. The advisory will credit the
reporter unless anonymity is requested.

## Out of scope

- Findings that require a compromised operator machine or stolen developer
  credentials.
- Reports generated by automated scanners without a demonstrated impact.
- Missing hardening in the local development configuration, including
  `LLM_PROVIDER_KIND=fake` and `OAUTH_TEST_MODE=true`, which configuration loading
  forbids in production.
- The absence of production infrastructure controls tracked as open milestone work
  in the production-readiness document.

## Reporting a code of conduct concern

The same private advisory channel may be used to raise a
[Code of Conduct](./CODE_OF_CONDUCT.md) concern. Mark the report clearly as a
conduct matter rather than a vulnerability.
